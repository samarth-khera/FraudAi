# FraudShield AI — Backend

> **SYNTHETIC DEMONSTRATION DATA.** All accounts, transactions, and lineage values in the demo
> fixtures are synthetic scenarios. They do not represent real bank customers or real financial movements.
> This prototype is for demonstration and decision support only; it is not production-bank software.

---

## Purpose & Principles

When a fraud is reported, funds often hop rapidly through multiple intermediate accounts.
**FraudShield AI** provides a persistent case management system, deterministic downstream fund-tracing
engine, ML-driven risk scoring, and an application-level append-only audit trail (not cryptographically protected).

Key Principles:
1. **Fairness & Innocent-Recipient Protection**: Receiving money connected to a reported fraud does **not** make an account owner a fraudster.
2. **Separation of Concepts**: Fraud indicators, fund exposure, evidence quality, and review status are kept strictly separate.
3. **Decision-Support Only**: Risk scores and tracer outputs assist human investigators. The system **never** automatically freezes accounts, seizes funds, or issues guilt verdicts.
4. **Append-Only Auditing**: Every state change (case creation, metadata update, batch transaction ingestion, reviewer assessment, trace calculation) is logged immutably.

---

## Database Architecture

- **Engine**: SQLite for local zero-cost setup (`fraudshield.db` via `DATABASE_URL`).
- **PostgreSQL Compatibility**: Built using **SQLAlchemy 2.0 ORM** and clean relational abstractions. Changing `DATABASE_URL` to a PostgreSQL connection string requires zero changes to core business logic.
- **Migrations**: **Alembic** manages schema versioning and database migrations.
- **Relational Schema**:
  - `fraud_cases`: Case metadata, reported origin transaction, reported amount, currency, investigation status (`open`, `under_investigation`, `closed`).
  - `accounts`: Neutral account records (`account_id`, `label`, `role`, `is_synthetic`).
  - `transactions`: Immutable financial movements (`transaction_id`, timestamp, sender/receiver foreign keys, amount, type, optional synthetic lineage).
  - `account_review_statuses`: Human investigator assessments (`review_state`, `evidence_quality`, `notes`, `reviewer_id`, `automated_action_taken`).
  - `audit_events`: Append-only through the API (not tamper-proof) historical log (`event_id`, `case_id`, `timestamp`, `action`, `performed_by`, `entity_type`, `entity_id`, `details_json`).
  - `case_trace_paths`: Persisted fund-flow paths and hop calculations generated by the tracing engine.

## Local Setup & Migrations

### 1. Environment & Dependencies

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Database Migrations

Apply Alembic migrations to create or update all database tables:

```bash
cd backend
alembic upgrade head
```

To configure an external database (e.g., PostgreSQL):
```bash
export DATABASE_URL="postgresql+psycopg2://user:password@localhost:5432/fraudshield"
alembic upgrade head
```

### 3. Initialize Demo Data

On application startup, the database is automatically and **idempotently seeded** with the synthetic demonstration case `FS-1042`. Restarting or re-running the seeder never duplicates existing cases or transactions.

To manually seed via Python:
```python
from app.db.session import SessionLocal
from app.db.seed import seed_demo_data

with SessionLocal() as session:
    seed_demo_data(session)
```

## API Endpoints

The OpenAPI schema at `/docs` (development only) is generated from the source and is the authoritative contract.
**Write** endpoints go through `verify_write_permission` (see *Write access and reviewer identity* below);
everything else is read-only and needs no key.

### Cases, reviews and audit

| Method | Path | Write | Description |
|---|---|---|---|
| `GET` | `/health` | | Service status, plus `write_access` (how writes are protected) |
| `POST` | `/api/cases` | yes | Create a case (records an audit event) |
| `GET` | `/api/cases` | | List cases with dataset and review progress (`?skip=0&limit=50`) |
| `GET` | `/api/cases/{case_id}` | | Case details, account dataset, review progress |
| `PATCH` | `/api/cases/{case_id}` | yes | Update status or description (records an audit event) |
| `POST` | `/api/cases/{case_id}/transactions` | yes | Add observed transactions (rejects conflicting duplicates) |
| `PUT` | `/api/cases/{case_id}/accounts/{account_id}/review` | yes | Record a review decision; the account must be part of the case |
| `GET` | `/api/cases/{case_id}/accounts`, `…/accounts/{account_id}/assessment` | | Evidence-aware account assessments |
| `GET` | `/api/cases/{case_id}/audit-trail` | | The case's audit events |
| `GET` | `/api/audit`, `/api/audit/export.csv` | | Search and export audit events across cases |

### Fund tracing

| Method | Path | Write | Description |
|---|---|---|---|
| `GET` | `/api/cases/{case_id}/transactions`, `/graph`, `/trace` | | Traced transfers, graph and paths (`/trace` and `/graph` store paths; an audit event is written only when they change) |
| `GET` | `/api/v2/trace` | | Trace any synthetic-ledger account |

### Synthetic ledger accounts and models

| Method | Path | Write | Description |
|---|---|---|---|
| `GET` | `/api/v2/accounts/{id}`, `/transactions` | | Ledger profile and transactions (PII masked) |
| `GET` | `/api/v2/accounts/{id}/assessment` | | Rule score (points out of 100) |
| `GET` | `/api/v2/accounts/{id}/ml-assessment` | | Account model score and TreeSHAP factors; `503 model_unavailable` if the model cannot load |
| `POST` | `/api/v2/accounts/{id}/analyze` | | Live analysis (below). Computes from the ledger and stores nothing, so it is available in every write-access mode. |
| `GET` | `/api/v2/models/status` | | Model versions, served thresholds, evaluation metrics |
| `POST` | `/api/v2/investigations` | | Victim-first investigation: flags, time-ordered trace, per-account rule + model assessment, exposure range, evidence-referenced findings, plus an optional Gemini explanation in `ai_analysis` (`state` says whether it ran; see [docs/AI_ANALYST.md](../docs/AI_ANALYST.md)). Stores nothing; available in every write-access mode. See [docs/LIVE_INVESTIGATION.md](../docs/LIVE_INVESTIGATION.md). |
| `POST` | `/api/v2/investigations/explanation` | | AI explanation for the same investigation, recomputed on the server; returns `report_digest` + `ai_analysis`. Stores nothing. |
| `GET` | `/api/v2/data-source` | | Which ledger is queried, whether it is synthetic, record counts and `data_as_of` (fresh query) |
| `POST` | `/api/risk/score`, `/api/risk/explain` | | PaySim transaction benchmark (separate from the account model) |

### Live analysis response (`POST /api/v2/accounts/{id}/analyze`)

| Field | Meaning |
|---|---|
| `ml_assessment.risk_score` | Account **model score**, 0–100%. Uncalibrated; **not** a probability of fraud. |
| `ml_assessment.predicted_class` | `suspicious` = at or above the served review threshold; `legitimate` = below it. Not a finding. |
| `rule_assessment.risk_score` | **Rule score**, points out of 100. `risk_level` `high`/`critical` means the rules suggest review. |
| `divergence.model_suggests_review` / `rule_suggests_review` | Each check's own review suggestion. |
| `divergence.checks_disagree` | Exactly one of the two checks suggests review. |
| `divergence.model_review_threshold` | Threshold of the served model on its 0–1 scale, read from model metadata (0.1752 for `v2-account-2.0.0`). |
| `divergence.model_score_unit` / `rule_score_unit` | `percent_0_100_uncalibrated` / `points_0_100`. |
| `human_review_recommended` | True if the model or the rules suggest review, or quick forwarding was observed. |
| `human_review_basis` | Which of those applied: `model_at_or_above_threshold`, `rules_high_or_above`, `rapid_pass_through_observed`. |
| `divergence.divergence_detected` | **Deprecated** alias of `checks_disagree` (same value). |
| `divergence.score_delta` | **Deprecated, not meaningful.** `abs(ml_score − rule_score)` subtracts rule points from a model percentage. Kept with its original arithmetic only so existing callers do not break. Do not display or compare it. |

The two scores are on different scales. Compare the review suggestions, never the numbers.

### Write access and reviewer identity

`GET /health` reports `write_access`:

| `write_access` | When | Behaviour of write endpoints |
|---|---|---|
| `open_local_development` | No `ADMIN_API_KEY`/`FRAUDSHIELD_API_KEY`, `ENVIRONMENT` not `production` | Accepted without a key. The server logs a warning. **Local use only; do not expose publicly.** |
| `api_key_required` | A key is configured | Require `X-API-Key: <key>` or `Authorization: Bearer <key>`; otherwise `401 unauthorized`. |
| `disabled_no_key_configured` | `ENVIRONMENT=production` and no key | Refused with `503 write_access_not_configured` (fails closed). |

- A key proves only that the caller holds the shared key. There are no user accounts or roles.
- `reviewer_id`, `updated_by`, `created_by` and `added_by` are **self-reported names**. They are never verified.
  Names the application uses itself (`system_seeder`, `tracer_service`, `api_key_admin`, `local_dev_user`) are
  rejected with `422`.
- Every audit event from a client write records `reviewer_name_source: "self_reported"`,
  `request_authenticated` (whether a valid key was used), and `auth_method`. `reviewer_identity_verified` /
  `actor_identity_verified` are kept for older readers and are always `false`.
- The bundled web app never sends a key. With a key configured it can read but not write, and it says so.

### Audit integrity

Audit events are added in the same database transaction as the change they describe: a refused or failed write
leaves no audit event. The API has no endpoint to edit or delete events. This is **application-level
append-only**, not tamper-proof storage: anyone with access to the SQLite file can change it, and events are not
signed or hash-chained. Timestamps are server-generated UTC.

## Security, Fairness & Limitations

1. **Authentication & Authorization**: There are no user accounts, sessions or roles. Writes are protected by
   one shared API key when configured (see *Write access and reviewer identity*); reviewer names are self-reported.
   Do not expose the service publicly without a key and a TLS-terminating reverse proxy.
2. **Append-Only Auditing**: The API cannot edit or delete audit records. This is not cryptographic immutability.
3. **No Automated Actions**: High risk scores or graph connections **never** automatically freeze accounts or seize funds. They are strictly decision-support signals for accredited compliance investigators.
4. **Data Isolation**: The repository layer rejects conflicting transaction payloads (same transaction ID with altered amounts or parties) with a `409 Conflict` to prevent ledger tampering.
